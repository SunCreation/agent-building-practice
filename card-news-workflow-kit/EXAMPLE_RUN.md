## AI 최신소식으로 제작과 검수

이제 만든 앱에 **‘AI 최신소식’**을 입력해 카드뉴스 한 편을 완성합니다. 이 실습의 시작점은 정해 놓은 모델이나 오래된 발표가 아닙니다. 실행 시점을 기준으로 최근 7일의 소식을 검색하고, 그중 설명할 가치가 있는 소식을 1~3개 고릅니다. 앱의 제작 에이전트는 조사부터 이미지와 원고 생성까지 이어서 수행하고, 학생은 선택이 필요한 지점과 최종 결과를 확인합니다.


아래 과정은 만든 앱이 자동으로 이어 가야 할 동작입니다. 사용자는 주제를 입력하고 필요한 선택과 승인을 합니다. 인용된 요청문은 각 단계를 수동으로 진행하라는 뜻이 아니라, 앱에 동작이 빠졌거나 수정이 필요할 때 개발 도우미에게 전달할 참고입니다.

### 1. 주제를 입력하고 후보를 고릅니다

앱에서 주제에 ‘AI 최신소식’만 입력합니다. 에이전트가 검색 기준일과 검색 기간을 화면에 표시하고, 가능하면 서로 다른 후보 7~12개를 제시하는지 확인합니다. 같은 발표를 다룬 기사는 묶고 모델·제품·연구·개발 도구 등으로 후보가 다양하게 구성됐는지 살펴봅니다. 각 후보에는 제목, 원문 링크, 게시일, 실제 발표·변경일(확인되는 경우), 선택할 가치와 불확실성이 필요합니다. 확인하지 못한 날짜는 미확인으로 표시합니다. 최근에 작성된 소개 글이라고 해서 오래된 발표를 새 소식으로 분류하지 않습니다. 기간 안에 확인 가능한 소식이 부족하면 실제로 찾은 수를 알리고, 검색 기간을 30일로 넓힐지 선택하게 합니다.

> 실행 시점을 기준으로 최근 7일의 AI 소식을 찾아 줘. 가능하면 서로 다른 후보 7~12개를 다양하게 찾아 원문과 날짜, 선택할 가치와 불확실성을 보여 줘. 부족하면 실제로 찾은 만큼만 알려 줘.

**확인할 것:** 후보의 공식 원문을 직접 하나 열어 제목과 날짜를 대조합니다. 검색 결과 요약만 있고 원문을 읽지 못했다면 ‘검증 완료’로 넘어가면 안 됩니다.

### 2. 선택한 소식을 심층 검증합니다

후보 1~3개를 선택하면 에이전트가 공식 발표뿐 아니라 관련 제품 문서·변경 기록도 확인하도록 합니다. 무엇이 달라졌는지, 누가 언제부터 사용할 수 있는지, 지역·계정·요금제 등의 조건이 있는지를 분리합니다. 성능이나 효과를 소개할 때는 발표 주체의 주장인지 독립적으로 확인한 사실인지 구분합니다. 서로 다른 자료의 날짜나 조건이 맞지 않으면 카드 원고를 확정하기 전에 불일치를 보여 줍니다.

> 선택한 후보의 변화와 사용 조건을 원문으로 검증해 줘. 확인한 사실, 발표 주체의 주장, 아직 확인하지 못한 내용을 나누고 근거 링크를 붙여 줘.

**확인할 것:** ‘모두 사용 가능’, ‘무료’, ‘성능 향상’처럼 의미가 큰 문장을 골라 근거와 대조합니다. 모르는 부분을 그럴듯한 문장으로 채우지 않는지 봅니다.

### 3. 독자와 후킹 방향을 판단합니다

검증을 마친 뒤에 표지 문장을 만듭니다. 에이전트는 선택한 소식과 조사 결과를 바탕으로 대상 독자를 판단하고 추천 이유를 제시합니다. 독자나 편집 방향에 따라 결과가 크게 달라질 때만 짧은 객관식 질문을 제시합니다. 예를 들어 일반 사용자·개발자·교육자 중 누구에게 전달할지 묻고, 선택의 차이를 한 줄로 설명하며 자유 입력도 허용합니다. 예를 들어 실제 사용법을 알려 줄지, 변화의 의미를 설명할지에 따라 카드 구성이 크게 달라진다면 ‘직접 써보기’와 ‘변화 이해하기’ 중 선택하게 할 수 있습니다. 이미 목적을 입력했다면 같은 질문을 반복하지 않습니다.

> 이 소식에 적합한 독자와 관심을 가질 이유를 판단하고 표지 문장 2~3개를 제안해 줘. 방향이 모호할 때만 선택지로 물어봐 줘. 확인하지 않은 효과는 제목에 넣지 마.

**확인할 것:** 표지만 읽었을 때 원문보다 기능이나 혜택을 크게 받아들이게 되지 않는지 확인합니다. 궁금증을 만드는 문장과 사실을 과장하는 문장을 구분합니다.

### 4. 스토리보드를 확인하고 이미지를 생성합니다

선택한 형식으로 보통 5~8장의 스토리보드를 만들고 내용에 맞게 조정합니다. 예를 들어 표지 → 달라진 점 → 활용 상황 → 사용 조건·한계 → 요약과 출처 순서로 구성할 수 있습니다. 각 장에는 핵심 문장 하나, 짧은 본문, 이미지의 역할, 근거 링크를 표시합니다. 모든 장에 같은 정보를 반복하거나 이미지로 설명할 수 없는 추상적인 지시만 들어가지 않았는지 확인합니다.

> 선택한 형식으로 5~8장 스토리보드를 만들어 줘. 각 장의 핵심 문장, 본문, 이미지 역할, 출처를 보여 주고 한 장에 메시지 하나만 담아 줘.

스토리보드를 확정하면 앱의 제작 에이전트가 **Antigravity CLI(`agy`)를 통해 이미지 생성을 요청**하도록 합니다. 이미지 요청에는 장면, 공통 색감, 구도, 글자를 올릴 여백을 포함하고 ‘이미지 안에 글자 없음’을 명시합니다. 실제 제품 화면이나 발표 장면이 아닌 그림은 설명용 생성 이미지로 기록합니다. `generate_image`는 에이전트의 이미지 생성·편집 도구이며, 별도의 `agy image generate` 명령으로 설명하지 않습니다. [공식 도구 문서](https://www.antigravity.google/docs/sdk/tools/)

> 이 스토리보드에 맞는 설명용 이미지를 agy로 생성해 줘. 장마다 색감과 그림체를 통일하고, 제목을 올릴 여백을 남겨 줘. 이미지 안에는 글자를 넣지 말고 실제 저장 파일을 확인해 줘.

**확인할 것:** 앱이 요청을 보냈다는 사실과 이미지 파일이 생성됐다는 사실을 구분합니다. 생성 결과의 파일이 존재하고 실제 이미지로 열리는 것을 확인한 뒤에만 완료로 표시해야 합니다. 생성 실패 시 해당 카드에 오류와 재시도 버튼을 보여 주고, 확정한 스토리보드와 다른 카드의 결과는 유지합니다.

Headless는 대화형 화면 없이 요청을 실행하는 방식입니다. 이 실행에서는 필요한 도구 권한을 대화형으로 받을 수 없어 작업이 거부될 수 있습니다. 종료 코드나 응답 문장만으로 이미지 생성 성공을 판단하지 말고 결과 파일까지 검증합니다. 인증 실패는 대화형 `agy`에서 로그인을 확인하고, 권한 거부는 필요한 도구의 허용 규칙을 설정한 뒤 재시도합니다. 승인한 작업을 별도 작업 폴더에서 시험할 때는 해당 실행에 `--dangerously-skip-permissions`를 추가하는 방법도 있습니다. 이 옵션은 이미지 도구에만 권한을 주는 것이 아니라 그 실행의 모든 도구 요청을 자동 승인합니다. 웹 서비스에 연결할 때는 필요한 도구만 허용하는 규칙을 우선 사용합니다. [Headless 실행과 권한](https://www.antigravity.google/docs/cli/headless/), [설치와 인증](https://www.antigravity.google/docs/cli/install/)

앱의 자동 연결을 점검하거나 같은 요청을 터미널에서 확인할 때 참고합니다. 작업 폴더에서 `agy`를 실행해 대화형 세션의 인증을 먼저 확인합니다. 다음은 공식 `-p` 형식으로 자연어 요청을 전달하는 예시입니다. 환경의 인증과 권한에 따라 실행 결과가 달라지므로 이미지 파일 생성 여부를 직접 확인합니다.

```bash
agy
```

대화형 세션을 종료한 뒤 일회성 요청은 다음 형태로 전달할 수 있습니다.

```bash
agy -p '내장 generate_image 도구로 AI 소식을 설명하는 카드뉴스용 일러스트를 만들어 줘. 청색과 흰색, 단순한 구도, 위쪽 제목 여백, 이미지 안에 글자 없음. 현재 작업 폴더의 card-01.png로 저장하고 실제 저장 경로를 알려 줘.'
```

`card-01.png`는 자연어로 요청한 저장 위치입니다. 반환된 경로와 파일을 다시 확인합니다. `--output-format json`은 CLI 응답 형식이며 이미지 파일 형식 옵션이 아닙니다. headless 실행 중 권한이 거부되면 `permissions.allow` 규칙으로 필요한 도구를 허용할 수 있습니다. 승인한 시험 작업에서 이번 실행의 모든 도구 요청을 허용하려면 위 명령 끝에 `--dangerously-skip-permissions`를 붙입니다. 이 플래그는 전역 설정 파일을 바꾸지 않으며, 작업 폴더 자체가 보안 격리를 제공하는 것은 아닙니다. ### 5. 글자를 별도로 넣고 미리보기를 수정합니다

생성한 이미지는 배경이나 삽화로 배치하고, 제목·본문·출처는 앱에서 **편집 가능한 별도 텍스트 레이어**로 넣습니다. 그래야 맞춤법과 사실관계를 고칠 때 이미지를 다시 생성하지 않아도 됩니다. 모바일 크기로 전체 카드를 넘겨 보며 글자 크기, 줄바꿈, 여백, 명암 대비와 카드 사이의 흐름을 확인합니다.

> 생성 이미지 위에 제목과 본문을 별도 텍스트로 배치해 줘. 모바일 미리보기를 보여 주고 글자가 잘리거나 배경과 겹치는 부분을 수정할 수 있게 해 줘.

수정 요청은 카드와 문제를 구체적으로 지목합니다. ‘더 예쁘게’보다 ‘3번 카드의 본문이 길어. 핵심 조건을 유지하며 두 문장으로 줄여 줘’가 확인하기 쉽습니다. 이미지가 부적절할 때는 해당 카드만 다시 생성하고, 텍스트 수정만 필요하면 기존 이미지를 유지합니다.

### 6. 내보낸 파일로 최종 검수합니다

미리보기가 괜찮아도 내보낸 결과는 따로 확인합니다. 카드 이미지 파일을 모두 열어 순서와 수량, 글자 잘림, 한글 표시, 출처와 조사 기준일을 점검합니다. 자료를 재확인할 수 있도록 원문 링크와 이미지 생성 기록도 함께 보관합니다. 자동 게시까지 진행하지 않고, 수업에서는 검수한 파일을 결과물로 제출합니다.

| 검수 대상 | 통과 기준 |
|---|---|
| 최신성과 사실 | 조사 기간이 표시되고 핵심 문장의 날짜·기능·사용 조건을 원문에서 확인할 수 있습니다. |
| 독자와 흐름 | 표지가 독자에게 필요한 이유를 전달하고 각 카드가 서로 다른 메시지를 이어 갑니다. |
| 생성 결과 | 이미지 파일이 실제로 열리며, 생성한 그림을 실제 제품 화면이나 보도 사진처럼 설명하지 않습니다. |
| 편집과 가독성 | 제목·본문을 별도로 수정할 수 있고 모바일 크기에서도 글자가 읽힙니다. |
| 실패와 재시도 | 인증·권한·생성 실패가 완료로 표시되지 않으며 실패한 작업을 다시 시도할 수 있습니다. |
| 내보내기 | 확정한 카드가 빠짐없이 같은 순서로 저장되고 출처와 조사 기준일이 남습니다. |

> 내보낸 파일을 기준으로 누락, 글자 잘림, 출처, 날짜를 확인해 줘. 확인하지 못한 항목은 통과로 처리하지 말고 내가 확인할 부분을 알려 줘.
